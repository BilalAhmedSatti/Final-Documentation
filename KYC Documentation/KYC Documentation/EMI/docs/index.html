How this set is organised

  • It is a derivation, not a library. The domain justifies the journeys, the journeys justify the decisions, the decisions cite SBP — not the other way round.
  • It opens with what is still open. Legal and NADRA questions come before the machinery, because they are why some steps are tagged D instead of A.
  • Every note opens with a short brief. If you are not building this, read the brief and stop.
  • Every claim cites a circular or is marked as a pack choice. Unanswered things live in What We Do Not Know.
  • The decision log is the spine. No later page re-argues a decision; it links to one.

What we are building

A customer-facing wallet onboarding path: open, track, 2FA, consents, live photo, sanctions, NADRA, then a limit that matches the verification that actually ran. The wallet is e-money in a trust account. It is not a CIF deposit.

Three corrections we made

  1. Do not start at BV 400k. EMI §14 lets you issue on Verisys at 50k. CCOF footnote 1 leaves wallet limits in the EMI Regulations.
  2. Do not import bank debit-block as an EMI issuance rule. CCOF §F.1.c debit-block is a bank-style alternate. This pack does not use it as the EMI happy path.
  3. Do not treat BPRD 04 device bind as a KYC gate on E01/E02. EMI names CNIC/SIM pairing only at enhanced §14.III. 2FA is §12.II.

What this set is not

Not legal advice. Not a NADRA integration spec — do not invent APIs. Not the Conventional Digital Retail Bank pack in the parent folder. Ops queues, STR, and EDD casework live in 10-aml-risk-edd-ops.md, not in customer journeys.

Everything in this set is a zoom on one of these steps. If the step is not here, it is not customer onboarding.

  1. Open wallet. Application created. State INITIATED. Not a bank CIF.
  2. Tracking ID on screen. She can copy it. No SMS yet — no verified destination. See Tracking ID.
  3. Mobile OTP / 2FA. EMI §12.II. Fail stays INITIATED (UJ-E06). Success → CONTACT_VERIFIED, then SMS the Tracking ID.
  4. Consents + live photo. Live photo is A for digital open. Liveness/AI match is B/C. Not BV.
  5. Sanctions / TFS. Pre-screen. True match: no services, written decline, STR ops — not a UX retry.
  6. NADRA Verisys. CNIC verification. Wallet issues at PKR 50,000/month, cash-out 10,000/day. WALLET_ACTIVE · VERISYS. This is UJ-E01.
  7. Later: NADRA BV. Finger today; NADRA face only if operational. Same wallet, new limit 400,000 commercial. UJ-E02. Selfie does not do this.
  8. Optional: enhanced 1M. Commercial licence + PSP&OD. Annexure-J, CNIC/SIM pairing, TMS, CRP. Not outsourced. UJ-E03. See device binding.

Cash is a different clock

Verisys can open the wallet. Cash-in at agents/ATMs/branches and cash redemption still need NADRA BV (EMI §15). ATM cash-out always needs 2FA. Agent cash-out: BV, or 2FA if BVS is a major challenge.

Issuance CDD is EMI §12. The limit that follows is §14. Onboarding process overlay is the Consolidated Framework (BPRD C1/2025), including live photo, TAT, tracking ID, 30-day resume, and identity hierarchy — with wallet caps remaining in §14.

SBP: EMI Regulations §14.I–III (PSP&OD C3/2023, revised 21 Jun 2023). CCOF §F.1 is identity for opening or category upgrade — that is why E01, E02, and E03 are one onboarding ladder.

Minors are not this ladder

Basic minor: 50k Verisys, funded only from the guardian wallet. Enhanced minor freelancer: 400k BV. Adult §14.I–III enhanced limits do not apply to minors.

The EMI Regulations do not split finger and face. They only require biometric verification from NADRA. The split is CCOF §F.1, and it applies to EMI customers.

Three different faces

  1. NADRA facial BV — NADRA returns the match after footnote 6 is live. This is BV (A).
  2. CCOF live photo — capture at digital open (A). In addition to BV/Verisys, not instead.
  3. App liveness / AI match to CNIC photo — §K.iii encouraged (B/C). Not a BV substitute.

Public EMI paths (SadaPay, NayaPay) use in-app fingerprint BVS for the upgrade. That matches the pack: finger is BV; selfie is live photo.

Channel is D: in-app fingerprint, NADRA e-Sahulat, or partner ATM are equivalent if the call is NADRA BV. SBP does not require a particular SDK.

Until NADRA writes that face is on

Treat multi-finger as the only face of BV for 400k, cash-in, and cash redemption. Unclear prints go to the Verisys alternate (UJ-E07), not to “use the selfie camera as BV.”

Not in this log: minting Tracking ID only after OTP. That is an option Legal may take. It is not signed. See the open register.

Create the ID when the application starts. Do not SMS it until OTP succeeds. Those are different events.

What is A

CCOF §I.2–I.4: a tracking ID is generated, the customer is notified of account opening initiation, and they can check status on app/web (and branch systems if you have them). TAT is 2 working days from a complete file, not from when you mint the ID. Resume incomplete sessions for 30 days (§J.iii).

What this pack does

Open wallet
  → create application + Tracking ID     generate (on screen)
  → mobile OTP / 2FA                     EMI §12.II
  → SMS Tracking ID                      first out-of-band notify

SMS before OTP would go to an unbound number (typo, someone else’s SIM, enumeration). CCOF §K: do not leave onboarding artefacts on an untrusted channel.

Can we create it only after OTP?

No clearance. SBP does not say “before OTP” and does not say “after OTP.” If Legal defines initiation as CONTACT_VERIFIED, mint + notify at that instant can still meet §I for the success path — that is what the J1–J12 PDF does for SMS.

If Legal defines initiation as the first tap, minting after OTP is a §I.2 gap. You also lose a customer-facing ID on OTP fail (UJ-E06) unless a session token covers 30-day resume.

Until that interpretation is signed, this pack keeps generate at Step 0, SMS after OTP.
