System Requirements & Architecture (SRS)

EMI onboarding, KYC engine, and compliance admin portal — written for the Zeki EMI digital wallet model (NayaPay / SadaPay style). Phase 1: Pakistan. Phase 2: global expansion.

In plain English

This SRS explains what the product must do: screens the customer sees, APIs the backend runs, how incomplete sign-ups are saved, how high-risk (PEP) people are reviewed, and what the compliance admin portal looks like.

Analogy: KYC Journeys (J1–J19) are the “airport security story.” This SRS is the “terminal blueprint” — counters, cameras, queues, and staff rooms.

Align with Pakistan rules

Some product tier examples below (e.g. Tier 0 without selfie) are product SRS illustrations. For licensed Pakistan EMI behaviour, prefer EMI §14 limits, verification ladder, and journey rules (live photo, NADRA BV vs Verisys, cooling-off). Official circulars on sbp.org.pk prevail.

Section 1 — What is an EMI?

An Electronic Money Institution (EMI) is a non-bank financial entity regulated by the central bank (in Pakistan: State Bank of Pakistan under EMI Regulations). It issues electronic money, stores customer funds in digital wallets, processes payments, and may issue branded debit cards (Visa / Mastercard / PayPak).

1.1 Key operational constraints

Stored value — no interest

EMI wallets are non-interest-bearing stored-value accounts. Funds are safeguarded — not bank deposits earning return.

No lending from deposits

EMIs cannot issue credit cards, overdrafts, or loans funded from customer e-money balances.

Onboarding screens & backend APIs

Step-by-step UI sequence and the APIs that run behind each screen.

In plain English

The customer walks through phone → OTP → PIN → CNIC camera → silent government/telco checks → liveness selfie → profile form → approved or “under review.” Each screen has one clear backend job. 

flowchart TD
    A[1.1 Mobile number] --> B[1.2 OTP verify]
    B --> C[2.1 Set MPIN]
    C --> D[3.1 CNIC front/back OCR]
    D --> E[4.1 Silent NADRA + PMD]
    E --> F[5.1 Liveness + face match]
    F --> G[6.1 Profile + AML screen]
    G --> H{Clean?}
    H -->|Yes| I[6.2 Approved · wallet]
    H -->|Flagged| J[Under review · EDD/PEP]

Phase 1 — Authentication & ownership

Screen 1.1 — Mobile number input

  • UI: Phone field with country code (+92).
  • Backend: Create cryptographically secure 6-digit OTP; send via licensed SMS gateway (Infobip / Twilio / local aggregator).
  • API: POST /api/v1/auth/send-otp

Screen 1.2 — OTP verification

  • UI: 6-digit OTP, auto-focus, 60-second resend timer.
  • Backend: Validate OTP against stored hash; issue temporary JWT registration_token; register device fingerprint.
  • API: POST /api/v1/auth/verify-otp
  • Rule: Wrong OTP never advances state (see J1 / fail-closed habits).

Phase 2 — Credentials & PIN

Screen 2.1 — MPIN creation

  • UI: 4- or 6-digit PIN + confirm.
  • Backend: Salted hash with Argon2id or bcrypt (work factor ≥ 12). Plain-text PIN never stored or logged.
  • API: POST /api/v1/user/set-pin

Phase 3 — Identity document capture (OCR)

Screen 3.1 — CNIC front & back

  • UI: Camera frame with glare/edge feedback and auto-capture.
  • Backend: Encrypt upload to object storage (e.g. S3); OCR parses CNIC number, name, DOB, issue & expiry dates.
  • API: POST /api/v1/kyc/cnic-ocr

Phase 4 — Government & telco verification (silent)

Screen 4.1 — Background processing / read-only review

  • UI: Progress (“Verifying with official databases…”). Optionally show non-editable OCR fields for sanity check before paid lookups.
  • Backend:
    1. NADRA Verisys — authenticity, demographics / official photo.
    2. PMD telco match — mobile number owned by that CNIC.
  • API: POST /api/v1/kyc/verify-identity

Phase 5 — Liveness & facial biometrics

Screen 5.1 — Active liveness & selfie

  • UI: Oval guide; blink / turn head / keep steady.
  • Backend:
    1. Liveness engine — block masks, screen replays, paper photos.
    2. Face match — CNN embeddings vs NADRA/CNIC face; example threshold ≥ 85%.
  • API: POST /api/v1/kyc/liveness-facematch
  • Product tiering (SRS): Completing this may upgrade Tier 0 → Tier 1. Skipping may leave Tier 0 — confirm against CCOF live-photo requirements for digital EMI.
  • Important: Face match / liveness is not NADRA fingerprint BV. Fingerprint BV is the biometric ladder for higher EMI bands (ladder).

Phase 6 — Compliance screening & provisioning

Screen 6.1 — Additional profile details

  • UI: Address, occupation / source of income, email, mother’s maiden name (and other Table-A / EMI fields as required).
  • Backend: AML + sanctions (UNSC, OFAC, local proscribed) + PEP screen; on clean status provision Stored Value Account (SVA) in core.
  • API: POST /api/v1/kyc/submit-profile

Screen 6.2 — Final status

  • UI: Success for instant approval, or “Under review” for flagged accounts.
  • API: GET /api/v1/kyc/status
  • Cooling-off: Pakistan digital banking controls still expect the 2-hour wait before full operation — see activation.

Drop-off handling & incomplete KYC

How the app remembers where the customer stopped — and how we re-check security before continuing.

In plain English

If the app crashes or the customer leaves, we save a draft under the same phone / application. We do not dump half-finished CNIC photos into the final customer table forever. After long gaps we force OTP / liveness again so a stranger cannot finish someone else’s pack. 

flowchart TD
    A[User re-opens app] --> B[GET /api/v1/onboarding/state]
    B --> C{Status}
    C -->|APPROVED| D[Wallet dashboard]
    C -->|PENDING| E[Under review screen]
    C -->|DRAFT| F[Resume at current_step]

3.1 Database strategy

Keep incomplete data in draft storage (PostgreSQL JSONB and/or Redis) so unverified profiles do not pollute production customer tables.

ColumnTypePurpose
user_idUUIDPrimary key
phone_numberVARCHARUnique; OTP-verified
kyc_statusENUMDRAFT · PENDING_EDD · APPROVED · REJECTED
current_stepENUMe.g. PASSCODE_SET · CNIC_UPLOAD · LIVENESS_CHECK · PROFILE_FORM
draft_dataJSONBScanned text, S3 URIs — temporary
last_active_atTIMESTAMPCleanup cron + nudge triggers

Journey mapping: resume ≤ 30 days with same Tracking ID is also J7.

3.2 Drop-off security rules

  1. TTL cleanup — S3 lifecycle deletes unverified ID images after ~30 days.
  2. Re-verification window — if idle > 24 hours, re-trigger sensitive steps (OTP and/or fresh liveness) before showing draft.

Re-engagement nudges

5–15 min idle / backgroundSession lockMPIN / device biometric to unlockIn-app

Edge cases

Device change mid-onboarding

New device fingerprint → invalidate old session → OTP ownership proof → then load draft on Phone B.

OCR / liveness retry exhaustion

After repeated failures, send tips / support chat (“glare-free photo”) instead of a generic nudge only.

Privacy reason

Do not keep unverified identity documents forever without active consent — purge drafts on the 30-day TTL.

PEP verification & EDD mechanics

Politically Exposed Persons can be onboarded — but never with a silent auto-approve. Journey mapping: J6.

Who is a PEP?

Someone with a prominent public role (e.g. MNA/MPA, senior judge, military general, SOE executive), plus close family and associates. They need Enhanced Due Diligence (EDD) and senior sign-off. 

flowchart TD
    A[User submits KYC profile] --> B[Screening · fuzzy PEP match]
    B -->|No match| C[Standard path]
    B -->|Match| D[Status = PENDING_EDD]
    D --> E[App: under compliance review]
    E --> F[EDD form · SoW / office details]
    F --> G[Compliance officer review]
    G --> H[MLRO sign-off]
    H --> I[Activate as High Risk · enhanced monitoring]

4.1 Workflow rules

  • Fuzzy match against PEP database — do not require exact spelling only.
  • Match → PENDING_EDD; app shows under-review copy (no tip-off of list names).
  • Push dynamic EDD form (source of wealth, public office details).
  • Webhook / case to Compliance Admin dashboard.
  • Officer rules out false positives (father name / CNIC / DOB).
  • MLRO (Money Laundering Reporting Officer) approves; account marked high-risk for ongoing monitoring (J10).

4.2 Fuzzy matching algorithms

AlgorithmBest for
Jaro-WinklerShort human names; rewards shared prefixes
LevenshteinEdit distance (insert/delete/substitute)
Soundex / MetaphonePhonetic matches (how the name sounds)

Typical similarity threshold in this SRS: about 75–80% to catch transliterations (Muhammad vs Mohammad).

4.3 Audit trail

  • Log every MLRO action, notes, and SoW attachments.
  • Immutable audit table; retain ~10 years for regulatory exams.
Never auto-approve a PEP match

False-positive clearing still needs a human. True PEPs need EDD + MLRO — see also SBP audit readiness.

6.1 Core KYC modules

Compliance → KYC Review

  • Queue filters: Pending / Approved / Rejected · account type · risk.
  • Review panel: CNIC images, OCR text, selfie vs NADRA match %, Verisys status, PMD telco match.
  • Actions: Approve · Reject (catalogue reason codes) · Escalate to EDD case.

Compliance → Cases

  • Workspace for PEP / sanctions-flagged files.
  • Request/review Source of Wealth; internal notes; route to MLRO digital sign-off.

Compliance → Alerts

  • Fuzzy name matches above threshold (e.g. 75%).
  • Duplicate CNIC / SIM flags.
  • Multiple failed biometric / liveness attempts.

6.2 Supporting modules

  • Customers — registry, tiers, historic KYC timestamps.
  • Accounts — wallet limits, freeze status, linked cards.
  • Audit Logs — immutable: Admin ID, time, IP, old→new state, notes (for SBP / internal audit).
